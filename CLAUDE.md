# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

GoalCurrent.live — a static, multi-page football (soccer) news/scores site (FIFA World Cup 2026, Premier League, UEFA Champions League) deployed on Vercel. It is **plain HTML/CSS/vanilla JS**, not a framework app: every route is a real file (e.g. `/premier-league/teams/index.html`), each page embeds its own `<style>` block plus shared `/css/*.css`, and behavior comes from `<script src="/js/*.js">` tags — there is no bundler, no `package.json`, and no client-side router. `/api/*.js` are Vercel serverless functions (Node, `export default async function handler(req, res)`).

## Commands

There is no build step, package manager, linter, or test runner in this repo (no `package.json`). Development is: edit HTML/CSS/JS directly, then verify.

- **Syntax-check a JS file before committing:** `node --check js/whatever.js` (this is the verification method used historically in this repo — see the many `*-VERIFICATION*.txt` / `*-AUDIT*.txt` files at the repo root, which are manual audit logs, not generated by tooling).
- **Preview locally:** open the HTML files directly, or serve the repo root with any static file server. `/api/*` endpoints only work under `vercel dev` (Vercel CLI) since they're serverless functions, not plain static files.
- **Type-check the `src/` TypeScript components:** `tsconfig.json` is configured with `noEmit: true` for `src/**/*.ts(x)` — run `tsc --noEmit` if a TypeScript compiler is available. These components (see below) are not currently wired into any page.
- `git branch -a` shows both `main` and feature branches — check current branch conventions before assuming `main` is checked out.

## Architecture

### Page structure (static HTML, repeated per section)
Content is organized by competition, each with the same sub-structure:
- `worldcup2026/` — `index`, `groups`, `fixtures`, `standings`, `teams`, `venues`, `bracket`, `countdown`, `favourites`, `news`
- `premier-league/` — `index`, `fixtures`, `results`, `table`, `teams` (with one subfolder per club, e.g. `premier-league/teams/arsenal/`), `news`
- `ucl/` — `index`, `fixtures`, `results`, `teams`, `news`
- `news/<slug>/index.html` — long-form articles, one folder per article
- `match/index.html`, `live/index.html` — generic match-detail / live-scores shells driven by query params and JS

When adding a page, copy the structure/conventions of a sibling page in the same section rather than inventing a new layout — header, subnav, ad rail, and footer markup/CSS classes (`gc-header`, `gc-subnav`, `gc-match-card`, `gc-section-label`, etc.) are expected to match across pages. `DESIGN-SPEC.md` documents the canonical colors/classes for subnav, featured-match cards, match-list cards, and section-title pills — apply `/css/gc-design-spec.css` after page-specific styles.

### Data flow: fixtures vs. scores vs. standings (critical — see `.cursor/rules/dynamic-scores-standings.mdc`)
**Never hardcode match results or standings.** The site enforces a strict separation:
- **Fixture metadata only** (teams, groups, UTC kickoff times, venues, broadcasters) lives in `js/worldcup-data.js` (`window.WC26`) — this file must never contain `homeScore`, `awayScore`, or `status: 'FT'`.
- **Finished results** are fetched from `/api/scores?results=wc` via `js/wc-results.js` and merged into `WC26.schedule` at runtime.
- **Live scores** come from `/api/scores?live=true` via `js/wc-live-poll.js`, layered on top as the `window.WC26_LIVE` overlay (polled every 30s client-side).
- **Standings** are always computed, never stored: `js/standings.js`, `js/groups.js`, and `WC26.computeStandings()` derive tables from the merged schedule + live overlay (sort: Points → GD → GF → alphabetical).
- After touching any of this sync logic, manually verify the groups hub, standings page, and a single group page show correct P/W/D/L/GF/GA/GD/Pts once the API responses load.
- Premier League standings follow an analogous but **completely separate** pipeline: `api/pl-standings.js` (league ID 39) must never reference WC26/UCL variables, and vice versa (see the file's own header comment).

### `/api/` — Vercel serverless functions
Each file is a standalone handler proxying/caching a third-party API; they intentionally don't share state:
- `api/scores.js` — api-football.com (api-sports.io) v3, World Cup league ID 1 / season 2026. Cache TTLs are tuned per query type and documented in the file header (live=60s, date/today=300s, finished results=3600s, single match=120s) — preserve these when editing to stay within API quota (7500 req/day).
- `api/pl-standings.js` — same api-sports.io provider, Premier League (league 39, season 2026), reads `FOOTBALL_DATA_KEY`.
- `api/news.js` — server-side RSS aggregation from BBC Sport / ESPN, filtered by a World Cup keyword list and auto-tagged (`INJURY`, `SQUAD`, `PREVIEW`, `RESULT`, `BREAKING`, `TRANSFER`, `NEWS`); never exposes raw RSS to the browser.
- `api/videos.js` — YouTube Data API v3 against FIFA's official channel, reads `YOUTUBE_API_KEY`.
- `api/subscribe.js` — POSTs new newsletter signups to Brevo, reads `BREVO_API_KEY` / `BREVO_LIST_ID`.
All handlers set CORS headers manually and return structured `{ error, message }` JSON on failure (config errors return 503/500, not a crash). API keys are read from `process.env` — never hardcode a key, and don't assume a `.env` file exists in this repo (none is committed).

### Shared client-side JS layer (`js/`)
- `js/gc-shell.js` — an **opt-in** standard app shell (header + sidebar) with a public `GCShell.init(...)` API; nothing renders unless a page explicitly calls it or sets `<body data-gc-shell="auto">`. This exists so shell changes don't silently affect every page.
- `js/gc-shared.js` / `js/gc-fix.js` / `js/gc-final-safe.js` — older/parallel navigation+sidebar implementations injected via `<style>` + DOM manipulation. Multiple overlapping nav systems exist (`gc-shell`, `gc-shared`, `global-sidebar.js`, `gc-flow-sidebar-counter.js`) — check which one a given page actually loads before changing shared nav/sidebar behavior, since not all pages use the same one.
- `js/gc-api.js` — the older multi-API integration layer (API-Football, football-data.org, TheSportsDB, RSS, plus `window.WC26` local JSON) with helpers like `GC.render.*`, `GC.watch()`, `GC.bracket()`, `GC.today()`. Some pages use this instead of / alongside the newer `/api/*` serverless proxies.
- `js/gc-flags.js` — the single global team-flag resolver (`GCFlags.code/url/img/normalize`); other files should use this instead of hardcoding ISO country codes.
- `js/gc-lang.js` (+ `lang/*.js`) — the i18n engine; each `lang/<code>.js` file supplies `window.GC_LANG` for one of 10 supported locales (en, fa, ar, fr, de, es, pt, it, nl, tr), including RTL languages (fa, ar) styled via `css/gc-rtl.css`. `js/gc-datetime.js` handles UTC→local kickoff-time conversion.
- `js/gc-consent.js`, `js/gc-favourites.js`, `js/notifications.js` — cookie consent, per-user favourite teams (localStorage), and push notifications (OneSignal via `OneSignalSDKWorker.js`).
- Several `*.bak` files exist alongside live versions (e.g. `js/gc-lang.js.bak`, `css/gc-rtl.css.bak`) — these are inactive snapshots, not loaded by any page; don't edit them expecting effect.

### `src/` — unintegrated TypeScript components
`src/components/{wc26,pl,match,shared}/*.tsx` and `src/lib/calendar.ts` (add-to-calendar / ICS helpers) are typed with `tsconfig.json` but are **not referenced by any `.html` or `.js` file** and have no build pipeline wiring them into the static pages. Treat this as a forward-looking/reference area, not live code — verify with a repo-wide search before assuming a component here is actually rendered anywhere.

### Deployment / infra
- `vercel.json` — canonical-domain redirects (`goalcurrent.online` → `www.goalcurrent.live`), a rewrite for `/match` → `/match/index.html`, and a strict `Content-Security-Policy` header covering the exact set of third-party origins in use (Google Analytics, AdSense, OneSignal, fonts). **Adding any new third-party script/API requires adding its origin to this CSP**, or it will be silently blocked in production.
- `sw.js` / `OneSignalSDKWorker.js` — service workers for the PWA (`manifest.json`); served with `no-cache` headers per `vercel.json`.
- `CNAME` — GitHub Pages-style custom domain file (`goalcurrent.live`); primary hosting is Vercel per `vercel.json`, so treat this as legacy/secondary unless told otherwise.
- `goalcurrent_cursor_project/` contains a one-off task brief for a **separate, older Next.js version of this project** (different repo layout: `public/`, `next.config.ts`). It is not the codebase you're working in — don't apply its instructions here, and note it contains credentials that should never be copied elsewhere.

## Conventions specific to this repo

- **No hardcoded scores/standings** — see the data-flow section above; this is the single most enforced rule in the codebase (`.cursor/rules/dynamic-scores-standings.mdc`).
- **Team flags**: always resolve via `GCFlags`/`WC26.flags`, never hardcode a flagcdn ISO code inline.
- **Header chrome color** (`#C8102E` on `.gc-header`, `.gc-section-header`, `.gc-hero`, `.fea-site-nav`) and the absence of a sidebar are treated as fixed brand decisions per `DESIGN-SPEC.md` — don't change them incidentally while fixing something else.
- When sharing shell/git commands with the user in this repo, put **one command per fenced code block** (no `&&` chains) so each is independently copyable — this repo's own `.cursor/rules/command-cards.mdc` convention.
